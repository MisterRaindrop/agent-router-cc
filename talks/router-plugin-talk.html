01 · 问题

直接对话 vs 用 router

让 Opus 亲自写每一行代码,贵,而且正确性只能靠你肉眼查。

问题直接提示 agent用 router
谁来执行Opus(贵)配额更多、更便宜的执行器(codex / sonnet)
改动范围只受提示词约束diff 上强制:允许的 glob + 改动行数上限
正确性你手动检查CLI 把关(范围+密钥+可执行位),Opus 在真实环境跑 build/测试
偷懒怎么办只能信模型的说辞主会话复审 diff,识别偷懒 / 错误的工作
改动落在哪立即写进工作区隔离 worktree;只有 land 才动你的分支
配额 / 限流运行卡住按真实剩余配额均衡;429 自动切换

router 从不自动合并 —— 门禁只决定 PASS / FAIL,是否 land 由你决定。

02 · 核心理念

最强的模型出判断,最便宜的配额烧 token

一个编码任务里,绝大多数 token 花在机械劳动上——读仓库、写实现、迭代到绿(实测:一个约 400 行的功能,执行侧就吃掉 1.88M 输入 token)。而真正需要顶级模型的——规划、复审、验证、合并——恰恰是低 token、高判断的部分。router 就是沿着这条线把工作切开的。

省下的 token 来自这个分工本身——不是找一个更便宜的模型替 Opus 做全部事情(那是拿质量换钱),而是让每一侧只花它真正值钱的那种资源。

03 · 额度怎么省

额度具体是怎么省下来的:四个机制

  1. 海量 token 落在便宜的池子里。执行器 CLI(codex / claude)用各自的订阅套餐登录,不需要 API key——跟主会话 Opus 的额度是不同的池子。实测执行侧总输入 19.16M token,一个都不从 Opus 的额度里走。
  2. 执行器的输出永不进入 Opus 的上下文。Opus 只读 diff 和交付报告,构建日志按路径引用而不粘贴——因为读进上下文的每一行,后面每一轮都要重付一遍,这是最大的一笔可避免成本。
  3. 一批任务只花一轮对话。独立任务一次 dispatch 并发跑完,墙钟取最慢者;编排器的对话轮次才是真正贵的东西,机械门禁能判掉的事,绝不多花一轮 Opus。
  4. 两个便宜池子之间再做均衡。codex 与 claude 按真实剩余配额轮流用,谁余量多谁先上,撞上真实 429 自动切换——省下的不只是额度,还有"额度用光只能干等"的墙钟。

06 · 编排(一) · 任务契约

档位(tier)与风险(risk),是两个不同的问题

问题决定什么
tier这活需要多强的能力?挑选模型与推理强度
risk做错了有多糟?挑选独立复审的深度

对认证路径的机械式改动,是 weak 且 high。router 按真实剩余配额在档位内挑执行器 —— 配额从不会把任务降级到更弱的模型;风险只会被证据升级,从不会被调低。

风险档位、Must NOT、Verification Matrix —— 走设计流时,这些在 /router:plan 的任务拆分里就定好;日常任务由 /router:go 凭你们对话的完整上下文现场拆解。两条路,契约都先于执行写进 task.yaml,不是 dispatch 时现拍的。

为什么是少而大的工作包,而不是碎任务

实测一个真实计划:拆成五个微任务,意味着五次执行器冷启动重新读一遍同一个仓库(一个约 400 行的功能,吃掉 1.88M 执行器输入 token),外加五轮复审往返。执行器从来不是瓶颈 —— 12.8 分钟的执行器时间,对着约三小时、~317 轮编排器对话。墙钟和成本,由编排器的对话轮次主导,机械门禁能判的事,不该多花一轮。

07 · 编排(二) · 并发与依赖

独立的任务并发跑,有依赖的排队等

实测:一个批次里 26s+31s 的两个独立任务,一起 dispatch 后墙钟是 32s;234s+244s 的一起跑是 244s —— 墙钟取最慢的那个,不是求和,而且只花一轮编排器对话,不是每个任务一轮。永远不要 fan out 到后台 shell 再自己去轮询——每一次轮询,都是一整轮编排器对话,那才是真正贵的东西。

08 · 设计流(一) · 两份文档

大特性:两份文档,按顺序批准

跨模块、有真实取舍的大特性,由你主动进入设计流 —— router 从不替你判断任务大小。分层思路借鉴 Superpowers(brainstorm → spec → plan);router 加上了对抗审核、逐节确认、版本绑定,和一条铁律:人裁决一切。

/router:design → DESIGN.md

为什么做、做什么、不做什么

  • 01澄清与调研交错 —— 一次只问一个问题;能问的不假设,能在代码里查证的不问,带回 file:line 证据
  • 02没收敛,不动笔 —— 对话仍开放时起草的文档,只是"带标题的猜测"
  • 032–3 个真方案摆开 —— 推荐一个,你来挑;被否掉的连同理由记入 Alternatives considered,审核时要用
  • 04七节逐节起草 —— 每写完一节停下,等你 approve / revise,才写下一节
  • 05批准即冻结 —— 之后任何修改 bump revision、要求重批;变更必须可见,绝不静默
/router:plan → PLAN.md

怎么做:步骤、拆分、验证、上线

  • 01门禁前置 —— Design 不是 design_approved 就拒绝生成:从未批准的设计推导计划,等于把猜测冻结成承诺
  • 02与设计版本硬绑定 —— frontmatter 记 design_revision;设计一动,Plan 自动打回草稿,绑旧版本的任务包被机器拒绝
  • 03验证矩阵 —— 每条验收标准映射到真正证明它的门禁;证不了的标 unverified,绝不用测不到它的测试糊弄
  • 04任务拆分按七要素预写 —— 目标 / 不变量 / 冻结接口 / 完成定义(含自带测试) / 文件范围 / 停止条件 / 版本绑定
  • 05批准后 go 逐字执行 —— 包清单在这里确认过,go 不再问第二遍

日常任务跳过这一切,直接 /router:go —— 是否走设计流,永远是你的决定。

09 · 设计流(二) · 对抗审核

Design Review:评审员戴着镣铐,裁决权在人

绝不自审 —— 换一个独立模型(优先非 Claude,如 codex)攻击方案本身:方向对不对、藏着什么风险、有没有更简单的路。这一页存在的原因是一次真实事故:一条错误的评审意见被静默采纳,改坏了正确的设计 —— 所以裁决是机制,不是承诺。

评审员的镣铐

  • 01必读 Alternatives considered —— 不许把已经否掉的路当新点子重提;认为否错了,要引述被否的理由再反驳
  • 02拿不准的,以问题提出 —— 不确定的事实绝不断言为错误;引具体处、说具体后果,不许喊"最佳实践"
  • 03每条异议结构化 —— {severity, confidence, argument, suggestion},逐条可裁决
  • 04没毛病就直说 —— 设计是健全的就明说,不许硬造异议凑数
  • 05用你的语言写 —— 批评和建议以对话语言输出,不把翻译负担丢给人

裁决协议

  • 06批评逐字打印 —— 从落盘文件读回,截断必续跑;半份批评绝不当完整呈现
  • 07逐条裁决:accept / reject / discuss —— 每个裁决记入 DECISIONS.md 留痕,附你的理由
  • 08裁决之前,零编辑 —— 按评审员的意思"顺手改进"是违约,不是主动性
  • 09没有自动收敛 —— 轮数你定,没有采纳阈值;评审员全票,也只是一个意见
  • 10跨轮 resume 同一评审员 —— 下一轮只发变更;它记得上轮异议,能核对"真的改了没"

后台运行,完整输出落盘到 critique-<n>.md;审的是 Design(方向),不是任务拆分 —— 拆分属于 Plan,不设对抗审核,因为方向已经定了。

11 · Review · 审核维度

绿灯之后的最后一关:两个镜头,16 条固定审核维度

真实案例

一次修复清过了 held-out oracle 测试、全部回归测试、以及 go 的及格线复审 —— 它的 guard 条件却写得比问题本身更宽,悄悄关掉了一个没有任何测试能看到的优化。/router:review 就是抓这种"全绿但判断差一格"的最后一道关:测试绿是前提,不是证据 —— 测试本身也是被审对象。

架构师镜头 · F1–F7 —— 功能与整体

  • F1需求真被解决了吗 —— 追完真实数据流再下结论;警惕"小而自信但改错地方"的 diff
  • F2该不该存在 —— YAGNI 到需求层:正确答案可能是"更小的需求 / 根本不用改"
  • F3复用还是重造 —— 重造已有 helper / 标准库 / 平台能力,是最常见的 slop
  • F4根因还是症状 —— 修在共享根上了吗?grep 每个调用者,兄弟调用点一起修
  • F5更简单但仍正确 —— 同等大小,选边界正确的那个
  • F6结构与集成 —— 实现有没有偏离方案、或暴露方案没想到的问题
  • F7独立正确性判断 —— 不信作者的测试;指出绿测试掩盖的正确性缺口

资深开发镜头 · D1–D9 —— diff 级手艺

  • D1健壮性 / 边界 —— 绿测试没覆盖的输入、顺序、并发、资源耗尽
  • D2失败模式 —— 错误是传播还是被静默吞掉?禁藏 bug 的 fallback
  • D3复杂度 / 过度设计 —— 比需要的更复杂更通用?"解释比代码还长 = 复杂度伪装成散文"
  • D4测试设计质量 —— 重新引入目标 bug 会挂吗?断言有意义还是同义反复?
  • D5可读性 / 命名 —— 不解释也能让下一个人看懂意图
  • D6与项目风格一致 —— 以周围代码为准,不是 reviewer 的口味
  • D7注释与捷径 —— 注释讲为什么;故意的捷径必须标"上限 + 升级触发条件"
  • D8安全 —— 注入、不可信输入、权限、资源生命周期
  • D9性能常识 —— 热路径上测试抓不到的 O(n²) / 逐行分配

两个镜头可以用不同的模型跑以增强独立性;各自出 findings,你对并集裁决。机械项(格式、import 顺序、编译过没过)不进 LLM 审 —— 交给 lint/CI,把判断力省给"测试是否有意义"这类问题。

12 · Review · 约束规则

Review:十条约束,把最后一关钉死

每条 finding 都是结构化的:{level, dimension, severity, location, what, why, suggestion, confidence} —— 逐字打印,你裁决。

复审怎么进行

  • 01前置检查先行 —— scope 漂移或标准未经批准:停,回 design / plan;绝不对着已经不匹配代码的标准审
  • 02绿灯是前提,不是证据 —— 测试本身也是被审对象,可能压根没测对东西
  • 03从 router 的记录出发 —— delivery header 缺失 = 合约违规,先查它;复审深度绝不低于有效风险(它只升不降)
  • 04引用日志路径,不粘贴日志 —— 贴进上下文的每一行,后面每一轮都要重付
  • 05决断 + 可执行,不 hedging —— location + 确切问题 + 具体后果 + 具体替换;说不出后果就降 confidence 或删掉这条

判决怎么下

  • 06阻塞要挣来 —— 只有功能错、健壮性、安全、或"测试抓不住它要防的 bug"才 blocking;没有就直说"可以 ship",不凑数
  • 07任何代码改动作废全部旧证据 —— 报告必须是对最终 head_sha 的一轮全新运行
  • 08反作弊契约 —— 不删不弱化测试;bug 修复先见 RED;不 mock 被测逻辑;没跑过的检查绝不标 pass,收了 0 个测试的运行不算通过
  • 09跨轮 resume,不橡皮图章 —— 核实每条 blocking 真解决:查新代码,不凭作者一句"改好了"
  • 10标准错了,回 design —— 验收标准绝不在 review 里被悄悄放宽来放行一个改动
轴取值回答什么
code_healthyes / needs-changes / no有没有代码缺陷
assuranceverified / partial / unverified有没有真的被证明

两条轴从不折叠成一个结论——"没找到缺陷"不等于"被证明了":一项必须验证的东西停在 unverified,assurance 最多只能是 partial。

13 · 模型怎么选

先定档位,再让真实配额在档位内挑执行器

档位codexclaude
weakgpt-5.6-terra · mediumhaiku · medium
stronggpt-5.6-sol · highsonnet · high
criticalgpt-5.6-sol · xhighopus · xhigh
  1. 先判断任务需要的最小能力档位——这是唯一重要的路由决定;判断错了也只会被证据往上修正,从不会被调低。
  2. 同一档位下,两个执行器都是候选,按真实剩余配额挑:余量多的先跑,打平看谁的窗口先重置;配额只在档位内部重排,从不降档,真撞上 429 才切到另一个。
  3. 推理强度跟着活儿走,不拉满:机械实现 medium,需要真本事 high,critical 才给 xhigh。实测:五个任务的一次计划在 xhigh/max 上花了 766 秒执行器墙钟,而契约早就把该做什么写清楚了。
  4. 编排器自己的模型(Opus)只出现在 critical 档位——当成普通执行器用,等于吃掉这整套路由机制本来要保护的那份预算。

design-review / review 的独立复审链

优先非 Claude(codex)保证独立;codex 不可用或超配额,才降到同强度的 claude/opus —— 绝不为了复审这件事把强度降下来。.router/models.yaml 可以覆盖任意一格,router models 显示解析后的结果表;没人会替你自动改它。

15 · 门禁(一)

便宜模型伪造不了的五道机械关卡

check含义
✓ diff_applies能否干净地 apply 到基线 commit
✓ scope只改了 allowed_globs、没超行数上限、没删测试
✓ secret_scan新增的行里没有密钥

16 · 门禁(二)

真实门禁是项目的属性,不是任务的属性

真实门禁,量出来的边界

真实 ClickHouse checkout 上,git status 显示 110 条:107 条构建残留、2 个未跟踪文件、真正未提交的改动只有 1 条。全拒绝,这个模式就没法用在它本该服务的项目上。热缓存 43GB。

真实配额均衡

codex 用量读自 ~/.codex/sessions,claude 用量读自 statusline 快照;余量更多的先跑,遇到真实 429 才切到另一个。queue 的吞吐上限是 1/T,与并发执行器数量无关。

18 · 教训 0.8.2

读代码看不出来的,只有跑起来才现形

缺陷一

usage 建议给"主模型"降档

router usage 曾建议把 ORCHESTRATOR 这一行路由到更便宜的档位 —— 但这一行的定义就是主模型本身,是唯一不可能被路由的一行,印在其它正确的提示旁边,毁掉的是整份报告的可信度。
修复:建议只看 dispatch 行。

缺陷二

land 留下空壳目录

land 删了运行的 worktree,却留下 .router/worktrees/<id>/。跑过的任务越多,空目录越多,读起来像一份"存活运行"清单。
修复:用 rmdir 收尾,非空目录自动跳过,第二次运行不受影响。

两处都不是读代码能看出来的问题 —— 是跑一次真实的端到端任务才现形的。版本号在同一次改动里一起提交:不提版本号,这两个修复永远到不了已安装的插件。

22 · 原则

从真实运行里蒸馏出来的几条硬规矩

绝不仅凭绿灯合并

一份既是绿色、又经过机械验证的 diff,主会话自己复审时仍挖出 3 个真实缺陷:一个并发数字跟实际跑的池对不上;一个批量 --json 路径把几份文档粘在了一起;一个测试 fake 读的环境变量根本不在执行器白名单里 —— 悄悄地什么都没证明。

读 diff,不读日志

diff 是判断的输入,要整份读完;原始构建日志只是证据,引用路径就够 —— 读进上下文的每一行,都会在后面每一轮被重新读一遍,是最容易避免、却最容易被忽视的成本。

机械门禁替代不了判断

便宜模型能在做错事的同时,轻松通过一个浅层门禁 —— 写死的值、空壳测试、误解的意图,这些从来不是"跑了没有"能回答的问题。
